# Лабораторная работа № 2. Открытые лицензии на программное обеспечение

**Цель:** познакомиться с понятием открытой лицензии, её видами и способами применения
открытых лицензий к программному обеспечению.

**Проект:** *Project Management* — курсовой проект, веб-приложение для управления
проектами по Scrum/Kanban (клиент — React 19 + TypeScript + Vite; сервер — Node.js +
Express 5 + Sequelize + PostgreSQL).
Репозиторий: <https://github.com/Skittels05/ProjectManagement>

---

## 1. Подбор лицензий

Использованные ресурсы:

- **SPDX License List** — <https://spdx.org/licenses/> — каталог лицензий с короткими
  идентификаторами (`MIT`, `Apache-2.0`, `GPL-3.0-only`, `AGPL-3.0-only` …), которые
  используются в поле `license` файла `package.json` и в заголовках
  `SPDX-License-Identifier`.
- **Choose a License** — <https://choosealicense.com/> — сравнение разрешений, условий и
  ограничений популярных лицензий.

### Исходные данные о проекте

| Характеристика | Значение |
|---|---|
| Тип ПО | Клиент-серверное веб-приложение (может работать как SaaS) |
| Назначение репозитория | Учебный проект, портфолио |
| Распространение | Исходный код на GitHub; бинарные сборки не распространяются |
| Патенты | Отсутствуют |
| Лицензии зависимостей | MIT (большинство), BSD-2-Clause (`dotenv`), BSD-3-Clause (`bcryptjs`), Apache-2.0 (`typescript`), Bitstream Vera (шрифты DejaVu) — все разрешительные |

Лицензии зависимостей проверены по полю `license` в `node_modules/*/package.json`;
итог — в [THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md). Copyleft-зависимостей нет,
поэтому проект можно выпустить под любой из рассматриваемых лицензий.

### Кандидаты

1. **MIT** (`MIT`) — разрешительная.
2. **Apache License 2.0** (`Apache-2.0`) — разрешительная с патентной оговоркой.
3. **GNU GPL v3** (`GPL-3.0-only`) — сильный copyleft.
4. **GNU AGPL v3** (`AGPL-3.0-only`) — сильный copyleft с «сетевым» условием.

**LGPL** (`LGPL-3.0-only`) рассмотрена и отброшена сразу: она предназначена для
библиотек, а наш проект — конечное приложение, которое никто не будет подключать
как библиотеку.

## 2. Сравнение

| Критерий | MIT | Apache-2.0 | GPL-3.0 | AGPL-3.0 |
|---|---|---|---|---|
| Тип | Permissive | Permissive | Strong copyleft | Strong copyleft (network) |
| Коммерческое использование | ✅ | ✅ | ✅ | ✅ |
| Модификация и распространение | ✅ | ✅ | ✅ | ✅ |
| Использование в закрытом (проприетарном) продукте | ✅ | ✅ | ❌ | ❌ |
| Сохранять уведомление об авторстве и текст лицензии | ✅ | ✅ | ✅ | ✅ |
| Указывать внесённые изменения | — | ✅ | ✅ | ✅ |
| Файл NOTICE | — | ✅ (если есть) | — | — |
| Явная патентная лицензия от авторов | ❌ | ✅ | ✅ | ✅ |
| Раскрывать исходный код производных работ | ❌ | ❌ | ✅ при распространении | ✅ при распространении **и при доступе по сети** |
| Производная работа под той же лицензией | ❌ | ❌ | ✅ | ✅ |
| Эффект для нашего веб-сервиса (SaaS) | нет | нет | нет («дыра SaaS») | обязывает открыть код модифицированного сервиса |
| Совместимость с зависимостями проекта | ✅ | ✅ | ✅ | ✅ |
| Отказ от гарантий и ответственности | ✅ | ✅ | ✅ | ✅ |
| Объём текста | ~170 слов | ~4 500 слов | ~5 600 слов | ~5 700 слов |
| Популярность на GitHub | №1 | высокая | высокая | низкая |

Краткая характеристика:

- **MIT** — «можно всё», единственное условие — сохранить копирайт и текст лицензии.
  Минимальный размер, понятна без юриста, де-факто стандарт для JS/TS-экосистемы
  (React, Express, Vite, Sequelize — все под MIT).
- **Apache-2.0** — те же свободы, плюс явная передача патентных прав и прекращение
  лицензии для того, кто подаёт патентный иск; требует отмечать изменённые файлы и
  сохранять файл `NOTICE`. Выгодна компаниям, у которых есть патенты.
- **GPL-3.0** — гарантирует, что все распространяемые производные версии останутся
  открытыми. Но приложение работает на сервере — пользователи получают доступ по
  сети, а не копию программы, поэтому для веб-сервиса GPL фактически не обязывает
  ничего открывать.
- **AGPL-3.0** — закрывает «дыру SaaS»: если модифицированная версия доступна
  пользователям по сети, её исходный код должен быть им предоставлен. Самая строгая;
  многие компании запрещают использовать AGPL-код.

## 3. Выбор: MIT

Для проекта выбрана лицензия **MIT**. Обоснование:

1. **Цель репозитория — портфолио и обучение.** Нужно, чтобы код можно было свободно
   смотреть, копировать фрагменты, форкать и использовать в других (в т.ч. учебных и
   коммерческих) проектах без юридических препятствий. MIT даёт максимальную свободу.
2. **Совместимость с экосистемой.** Почти все зависимости (React, Express, Sequelize,
   Vite, Redux Toolkit, dnd-kit, PDFKit …) распространяются под MIT, остальные —
   BSD/Apache. Лицензия проекта совпадает с лицензией его основы, конфликтов нет.
3. **Простота.** Текст из трёх абзацев, понятный без юриста; не нужно вести `NOTICE`,
   отмечать изменения в каждом файле или отслеживать, кто и как распространяет
   производные версии.
4. **Защита автора сохраняется.** MIT требует сохранять копирайт
   («Copyright (c) 2026 Uladzislau Petushkou») и содержит отказ от гарантий и
   ответственности — авторство защищено, а автор не отвечает за последствия
   использования кода.

Почему не другие:

- **Apache-2.0** — её главное преимущество (патентная оговорка) для проекта неактуально:
  патентов нет. Дополнительные формальности (NOTICE, пометка изменённых файлов) не дают
  выгоды.
- **GPL-3.0** — copyleft отпугивает тех, кто хотел бы переиспользовать код в своих
  проектах, а для серверного приложения, распространяемого как сервис, GPL почти ничего
  не гарантирует.
- **AGPL-3.0** — была бы логичным выбором, если бы цель была не допустить закрытых
  SaaS-клонов. Для учебного проекта это избыточно и сильно ограничивает повторное
  использование.

## 5. Готовность к загрузке на GitHub

Проверки перед публикацией:

- `LICENSE` лежит в корне репозитория — GitHub определит лицензию автоматически.
- `npm pkg get license` в `server/` и `client/` возвращает `"MIT"`.
- `git check-ignore server/.env` — реальные `.env` с секретами игнорируются;
  `node_modules/`, `dist/`, `uploads/` — тоже.
- `npx tsc --noEmit` в `server/` и `client/` — проект собирается с новыми заголовками.
- Изменения закоммичены в ветку `main`, remote `origin` указывает на
  `https://github.com/Skittels05/ProjectManagement.git`.

Публикация:

```bash
git push origin main
```

После этого на странице репозитория в блоке *About* появится «MIT license», а файл
`LICENSE` будет доступен по ссылке в README.

## 6. Ответы на контрольные вопросы

**1. Что такое открытая лицензия на ПО и чем она отличается от проприетарной?**

Открытая лицензия — юридический документ, которым правообладатель заранее разрешает
любому лицу использовать программу в любых целях, изучать и изменять её исходный код,
распространять оригинальную и изменённую версии при соблюдении условий лицензии.
Авторское право при этом сохраняется: лицензия — это управляемое разрешение, а не
отказ от прав. Проприетарная лицензия, наоборот, ограничивает использование
(число пользователей, устройств, цели), запрещает изучать, изменять и распространять
программу, исходный код обычно закрыт, а права получают за плату или по отдельному
договору.

**2. В чём разница между permissive (MIT, Apache) и copyleft (GPL) лицензиями?**

Permissive-лицензии требуют только сохранить уведомление об авторстве и текст
лицензии (Apache — ещё NOTICE и пометку изменений); производную работу можно
выпустить под любой лицензией, в том числе закрытой. Copyleft-лицензии требуют, чтобы
производные работы при распространении выпускались под той же лицензией с открытым
исходным кодом — свобода «наследуется» и её нельзя убрать. Поэтому GPL-код нельзя
включить в проприетарный продукт, а MIT/Apache-код — можно.

**3. Почему была создана LGPL? Когда она предпочтительнее GPL?**

LGPL создана для библиотек: при GPL любая программа, связанная с библиотекой,
становится производной работой и тоже должна выпускаться под GPL, что отпугивает
разработчиков закрытого ПО и мешает распространению библиотеки. LGPL разрешает
подключать (динамически линковать) библиотеку к программе с любой лицензией, требуя
открывать только изменения самой библиотеки и давать пользователю возможность
заменить её на свою версию. LGPL предпочтительнее, когда автор библиотеки хочет, чтобы
она стала стандартом и использовалась максимально широко (в т.ч. в коммерческих
продуктах), но при этом улучшения самой библиотеки оставались открытыми — например,
GNU C Library (glibc), FFmpeg, Qt.

**4. Чем AGPL отличается от обычной GPL?**

AGPL содержит дополнительное условие (раздел 13): если модифицированная программа
предоставляется пользователям для взаимодействия по сети, им должна быть предложена
возможность получить её полный исходный код. GPL срабатывает только при
распространении копий программы, поэтому SaaS-провайдер может изменить GPL-программу,
запустить её на своём сервере и не открывать изменения («дыра SaaS»). AGPL эту дыру
закрывает.

**5. Можно ли использовать GPL-программу внутри компании без открытия кода? А в
веб-сервисе?**

Да. Обязанности GPL возникают только при *распространении* (передаче копий) программы
третьим лицам. Внутреннее использование, в том числе с модификациями, распространением
не считается — открывать код не нужно (передача сотрудникам внутри одного юрлица
распространением обычно не считается). Если программа работает в веб-сервисе, по GPL
код тоже открывать не нужно: пользователи взаимодействуют с ней по сети, а копию
программы не получают. Исключение — код, который отдаётся в браузер (например,
JavaScript под GPL): он распространяется пользователям, и на него требования GPL
действуют.

**6. Можно ли использовать AGPL-программу внутри компании без открытия кода?**

Да. Пока программа (в том числе изменённая) используется только внутри компании и
доступна по сети лишь её сотрудникам, код не нужно публиковать: сотрудники работают с
ней от имени самой компании-лицензиата, а исходный код у компании и так есть
(формально требование раздела 13 при этом выполнено). Обязанность открыть код возникает, когда *изменённая* версия
становится доступна по сети пользователям вне компании (клиентам, партнёрам, публике)
— тогда им нужно предоставить исходный код этой версии. Немодифицированную
AGPL-программу можно запускать как публичный сервис, лишь сохраняя возможность
получить её исходный код (ссылку на оригинал).
